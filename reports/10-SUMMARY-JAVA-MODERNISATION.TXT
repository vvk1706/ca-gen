DLIS JAVA MODERNISATION — SUMMARY
==================================
Task: Decompose DLIS monolith into microservices, prepare for OpenShift on IBM Z / LinuxONE (zLinux),
      with lift-and-shift portability to x86 cloud. All original java/ source preserved unchanged.

Output directory: java-modernisation/


WHAT WAS BUILT
==============

4 MICROSERVICES + 1 SHARED LIBRARY
Decomposed exactly at the existing EJB service boundaries:

  Service                  Monolith origin         Owns table(s)              Port
  -----------------------  ----------------------  -------------------------  ----
  dlis-candidate-svc       CandidateServiceEjb     DLIS.CANDIDATE             8080
  dlis-application-svc     ApplicationServiceEjb   DLIS.LICENSE_APPLICATION   8080
  dlis-payment-svc         PaymentServiceEjb       DLIS.PAYMENT               8080
  dlis-approval-svc        ApprovalServiceEjb      DLIS.ISSUED_LICENSE        8080

  Shared library: dlis-common (domain objects: Candidate, LicenseApplication, ServiceResult<T>)


PLATFORM DECISIONS
==================

  Framework:   Quarkus 3.8.4 LTS
               - Red Hat certified on OpenShift 4.x
               - Jakarta EE 10 APIs (JAX-RS, CDI) — minimal code change from monolith
               - s390x UBI 9 base images from Red Hat registry
               - MicroProfile Health / OpenAPI / RestClient built-in
               - quarkus-jdbc-db2 extension wraps IBM DB2 JCC natively
               - ~0.8 s startup, ~100 MB footprint per pod (vs 60 s / 400 MB Liberty EAR)

  Java:        Java 17 LTS — IBM Semeru OpenJ9, UBI 9 openjdk-17-runtime
               (multi-arch manifest: s390x + amd64 from same image tag)

  Database:    DB2 schema DLIS — UNCHANGED
               All four services share the existing schema.
               Zero data migration risk in Phase 1.

  Why 4 services (not more/fewer):
               - 1:1 match with existing CA Gen action block boundaries
               - Payment and Application have different scaling profiles (I/O vs compute)
               - Approval + Issuance are a single atomic workflow — splitting adds no benefit
               - Shared DB schema makes 4 the natural split; 5+ would over-engineer


KEY CODE MIGRATIONS
===================

  Monolith pattern                          Modernised pattern
  ----------------------------------------  ----------------------------------------
  javax.ws.rs / javax.inject                jakarta.ws.rs / jakarta.inject (EE 10)
  @Stateless EJB                            @ApplicationScoped CDI bean
  @TransactionAttribute(REQUIRED)           @Transactional (Quarkus CDI)
  @Resource(lookup="jdbc/dlisDS")           @Inject DataSource (Agroal pool)
  server.xml JNDI / variable config         application.properties MicroProfile Config
  In-process EJB injection cross-service    MicroProfile @RegisterRestClient REST calls
  DlisApplication base path class           @Path("/api/v1/...") on each resource
  EJB service interfaces                    Removed — CDI bean IS the service

  All business logic preserved byte-for-byte.
  All SQL preserved unchanged.
  All HTTP status codes and error response formats preserved.

DEPLOYMENT ARTEFACTS
====================

  deploy/ocp/dlis-all.yaml
    Namespace: dlis
    ConfigMap: dlis-config (DB2_HOST, DB2_PORT, DB2_DBNAME, DB2_USER, service hostnames)
    Secret:    dlis-db2-secret (DB2_PASSWORD placeholder)
    Per service (x4): Deployment, Service, Route (TLS edge termination)
    - nodeSelector: kubernetes.io/arch: s390x
    - tolerations for mixed-arch clusters
    - readinessProbe / livenessProbe on /health/ready and /health/live
    - resources: requests 256Mi/100m, limits 512Mi/500m
    - replicas: 2

  Dockerfiles (per service)
    FROM registry.access.redhat.com/ubi9/openjdk-17:latest AS build (Maven build stage)
    FROM registry.access.redhat.com/ubi9/openjdk-17-runtime:latest (runtime)
    USER 185 (non-root — compatible with OCP restricted SCC)
    Quarkus fast-jar layout (/deployments/)
    Same Dockerfile rebuilds for linux/amd64 (lift-and-shift) without any changes


LIFT-AND-SHIFT TO X86 CLOUD
============================

  What changes:   Container image rebuild only (docker build or docker buildx)
  What is same:   All source code, SQL, business logic, REST API, environment variables,
                  Kubernetes Deployment/Service manifests, ConfigMap/Secret names

  Supported targets:
    - Amazon EKS         (use K8s Ingress instead of OpenShift Route)
    - Azure AKS          (same)
    - Google GKE         (same)
    - Red Hat ROSA       (OCP on AWS — dlis-all.yaml works unchanged)
    - IBM ROKS           (OCP on IBM Cloud — dlis-all.yaml works unchanged)
    - IBM IKS            (use K8s Ingress)

  DB2 options on x86:
    - IBM DB2 LUW 11.5 Community Edition on Linux x86 (identical SQL dialect)
    - IBM Db2 on Cloud (DBaaS, JDBC over SSL)
    - PostgreSQL migration path documented (~20 SQL changes, zero business logic changes)

  Multi-arch build (one command, both platforms):
    docker buildx build --platform linux/amd64,linux/s390x \
      -f dlis-candidate-svc/Dockerfile \
      -t registry/dlis/dlis-candidate-svc:2.0.0 --push .

INTER-SERVICE COMMUNICATION TOPOLOGY
=====================================

  application-svc ←── candidate-svc       (candidate validation on create/eligibility-check)
  payment-svc     ←── application-svc     (read app state, update payment status)
  approval-svc    ←── application-svc     (read app state, update approval/issue status)

  Transport:   HTTP/JSON via MicroProfile RestClient 3.0
  Discovery:   Kubernetes Service DNS (<svc-name>:8080 within dlis namespace)
  Config:      CANDIDATE_SVC_HOST / APPLICATION_SVC_HOST env vars (in dlis-config ConfigMap)


CICS BRIDGE
===========

  dlis-cics-bridge module — NOT migrated (out of scope for this phase)
  Reason: CICS Liberty JVM Server is a z/OS-only pattern; not containerisable.
  Path:   REST API microservices provide equivalent HTTP interface.
          A future thin CICS gateway service can proxy COMMAREA calls to REST endpoints.

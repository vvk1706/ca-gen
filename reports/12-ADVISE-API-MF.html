The Integration Layers

Regardless of the implementation language or product chosen, the same stack of layers sits between a REST client and the COBOL programs. The question is which layer you write yourself versus which is handled by a product.

REST Client
↓
API Gateway / Load Balancer  (optional)
↓
Integration Layer  ← this is what you're implementing
↓
Mainframe Transport  (CTG / MQ / z/OS Connect)
↓
CICS / COBOL Programs
↓
Db2 for z/OS

Option A — z/OS Connect EE (No Custom Code at All)

IBM's purpose-built product for exposing CICS, IMS, and batch programs as REST/JSON services. No application framework needed on either side — just descriptor files.

How it works

  • You provide a Service Provider Archive (SAR) — a JSON descriptor mapping REST fields to COMMAREA / channel fields.
  • z/OS Connect EE auto-generates an OpenAPI spec and handles all JSON ↔ COMMAREA transformation, EBCDIC conversion, and packed decimal encoding.
  • No COBOL changes required.

What you write

  • SAR descriptor files (JSON mapping definitions — one per COBOL program).
  • Optionally a thin API management layer (API Connect / Kong) in front for auth, rate limiting.
Trade-off: IBM licence cost is significant. If you have the licence, this is the lowest-effort path — hours to first working call versus days or weeks for a custom integration.

Option B — Node.js + IBM CICS Transaction Gateway

COMMAREA packing helpers

JavaScript
const iconv = require('iconv-lite');

// Fixed-length EBCDIC string (COBOL PIC X)
function packString(value, length) {
    const padded = (value ?? '').padEnd(length, ' ').slice(0, length);
    return iconv.encode(padded, 'cp1047');
}

// COMP-3 packed decimal — e.g. S9(10) COMP-3 = 6 bytes
function packComp3(value, digits) {
    const nBytes = Math.ceil((digits + 1) / 2);
    const buf = Buffer.alloc(nBytes, 0);
    const str = Math.abs(value).toString().padStart(digits, '0');
    for (let i = 0; i < digits; i++) {
        const nibble = parseInt(str[i]);
        const byteIdx = Math.floor(i / 2);
        if (i % 2 === 0) buf[byteIdx] = nibble << 4;
        else             buf[byteIdx] |= nibble;
    }
    // Sign nibble: 0xC = positive, 0xD = negative
    buf[nBytes - 1] = (buf[nBytes - 1] & 0xF0) | (value >= 0 ? 0x0C : 0x0D);
    return buf;
}

// COMP halfword S9(4) = 2-byte big-endian signed integer
function packComp(value) {
    const buf = Buffer.alloc(2);
    buf.writeInt16BE(value);
    return buf;
}

COMMAREA packing helpers

Python
import struct

def pack_string(value: str, length: int) -> bytes:
    """Fixed-length EBCDIC string (COBOL PIC X)."""
    padded = (value or '').ljust(length)[:length]
    return padded.encode('cp1047')

def pack_comp3(value: int, digits: int) -> bytes:
    """COMP-3 packed decimal. S9(10) COMP-3 = 6 bytes."""
    n_bytes = (digits + 2) // 2
    result = bytearray(n_bytes)
    abs_val = abs(value)
    digits_str = str(abs_val).zfill(digits)
    for i, ch in enumerate(digits_str):
        nibble = int(ch)
        byte_idx = i // 2
        if i % 2 == 0:
            result[byte_idx] = nibble << 4
        else:
            result[byte_idx] |= nibble
    # Sign: 0x0C positive, 0x0D negative
    result[-1] = (result[-1] & 0xF0) | (0x0C if value >= 0 else 0x0D)
    return bytes(result)

def pack_comp(value: int) -> bytes:
    """COMP halfword S9(4) = 2-byte big-endian signed."""
    return struct.pack('>h', value)

MQ transport via pymqi

Python
import pymqi

qmgr = pymqi.connect('QMGR01', 'CICS.REQUEST.QUEUE', '192.168.1.10(1414)')

def call_cics(program: str, commarea: bytes) -> bytes:
    md = pymqi.MD()
    md.ReplyToQ  = b'CICS.REPLY.QUEUE'
    md.MsgType   = pymqi.CMQC.MQMT_REQUEST
    q = pymqi.Queue(qmgr, 'CICS.REQUEST.QUEUE')
    q.put(commarea, md)
    # Receive from reply queue correlating by CorrelationId
    reply_q = pymqi.Queue(qmgr, 'CICS.REPLY.QUEUE')
    gmo = pymqi.GMO()
    gmo.MatchOptions = pymqi.CMQC.MQMO_MATCH_CORREL_ID
    gmo.WaitInterval = 5000  # 5 second timeout
    return reply_q.get(350, md, gmo)

COMMAREA packing helpers

Go
import (
    "encoding/binary"
    "fmt"
    "golang.org/x/text/encoding/charmap"
)

// packString — fixed-length EBCDIC (COBOL PIC X)
func packString(s string, length int) []byte {
    padded := fmt.Sprintf("%-*s", length, s)
    if len(padded) > length { padded = padded[:length] }
    enc := charmap.CodePage1047.NewEncoder()
    result, _ := enc.Bytes([]byte(padded))
    return result
}

// packComp3 — COMP-3 packed decimal, e.g. S9(10) = 6 bytes
func packComp3(value int64, digits int) []byte {
    nBytes := (digits + 2) / 2
    buf := make([]byte, nBytes)
    abs := value
    if abs < 0 { abs = -abs }
    s := fmt.Sprintf("%0*d", digits, abs)
    for i, ch := range s {
        d := byte(ch - '0')
        if i%2 == 0 { buf[i/2] = d << 4 } else { buf[i/2] |= d }
    }
    sign := byte(0x0C)
    if value < 0 { sign = 0x0D }
    buf[nBytes-1] = (buf[nBytes-1] & 0xF0) | sign
    return buf
}

// packComp — COMP halfword S9(4) = big-endian int16
func packComp(value int16) []byte {
    buf := make([]byte, 2)
    binary.BigEndian.PutUint16(buf, uint16(value))
    return buf
}

What Is Common Across All Options

Regardless of language or product, the same three layers are unavoidable:

1 — Mapper Layer (bulk of the work)

Translates JSON request fields into a packed byte buffer at exact byte offsets derived from the COBOL copybooks, and unpacks the response buffer back into JSON. One mapper per COBOL program. The hard sub-problems are:

  • COMP-3 (packed decimal) — digits stored two-per-byte with a sign nibble (0x0C = positive, 0x0D = negative). Affects CANDIDATE-ID, APPLICATION-ID, FEE-AMOUNT, etc.
  • EBCDIC ↔ UTF-8 — all PIC X strings are EBCDIC on z/OS. Every string field requires transcoding (Java Cp1047, Python cp1047, Go charmap.CodePage1047).
  • Fixed-length padding — COBOL strings are space-padded to their declared length. Serialiser must right-pad; deserialiser must trim() trailing spaces.
  • COMP binary fields — PIC S9(4) COMP = 2-byte big-endian signed; PIC S9(9) COMP = 4-byte big-endian signed.

2 — Transport Layer

The actual network call to CICS — via CTG, IBM MQ, or z/OS Connect. Roughly the same complexity in any language once the mapper is in place.

  • CTG (synchronous) — best for request/response flows. Native latency.
  • MQ (asynchronous) — better resilience; requires correlation-ID handling to present a synchronous REST interface.

3 — Orchestration Layer

For multi-step flows — the DLIS 5-gate pipeline — something must call program A, inspect the result, then conditionally call program B. The CICS menu (DLISMENU) handled this with screen navigation; the REST service layer replaces that with sequential service calls.

DLIS scope estimate: 10 mapper modules (one per COBOL program) × ~50–100 lines each = roughly 500–1,000 lines of integration code in any language, plus the REST router/controller layer on top. A focused team should have all mappers working and validated against live CICS in 2–4 weeks.
